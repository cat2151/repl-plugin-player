# ADR 0017: 変化するloopをRustのA/B演奏へ絞る

- 状態: 採用（timeline型と8個保持は撤回。A/Bの生成・破棄と1coreの稼働維持・TIME_CRITICALは[ADR 0019](0019-evolve2-async-pool.md)で置き換え済み）
- 決定者: user（両方式を試し、JSの周期に発音時刻を依存させず、自作側はkeyboard同様のRust DLLとする。演奏を途切れさせず次のランダム音色へcrossfadeするため、evolve mode内で4音源各2個を8trackへ配置して再利用する。同じ種類の音源でも現在音を鳴らしたまま別インスタンスで次の音色を準備できるようにし、準備が遅ければ現在音を保持する。8個同時発音時の音切れを受け、note onの送信対象は現在音と次の音色の最大2インスタンスだけとする。役目を終えた音源は無音になってから音符を終了してホスト側でbypassし、次音の準備時に復帰させる。通常起動と通常の演奏から分離し、終了用snippetを用意する）。その後userがtimeline型と8個保持を撤回し、Rust DLLだけに集中してA/Bの2個とする方針へ変更した。UAPMD拡張口と声部制約の探索方法、未公開graphを使う接続方法はAI
- 関連: [ADR 0014](0014-loop-in-project-archive.md)、[ADR 0019](0019-evolve2-async-pool.md)

## 決定と理由

穏やかな和音と転回形が時間で変化する演奏を、snippetを編集しながら育てたい。完成した独自シーケンサーを先に設計せず、timeline型と自作型の小さな入口を同時に試す。

timeline型は当初、標準clipに複数周の転回形を並べて反復した。既存の表示・編集・保存を使える一方、生成後の演奏が変化しないため、userの求めるevolveにはならなかった。1周分の標準clipを反復し、JSが周期的に転回形とoctaveの候補を選び直す方式へ変更する。発音時刻と音長を保持し、発音中の和音は更新せず、残りの音高だけを通常のclip編集経路で変更する。

自作型の発音をJSの定期callbackで駆動すると、JSや画面処理の遅延が発音時刻になる。userがこの方式を除外したため、JSはパターンを渡し、nativeがサンプル数を数えて次の発音を決める。AIはUAPMDの音声処理直前のイベント拡張口を利用し、時計までC++のUAPMD host DLL内に置いた。しかしuserが求めていたのはkeyboard同様のRust DLLであり、この責務配置を撤回する。時計・パターン管理・声部制約の探索を独立したRust DLLへ移し、C++はRustから直接扱えないUAPMDのイベント・ライフサイクルとの接続に限定する。依存checkoutは変更せず、ブロック内の時刻はUAPMDのUMP JR timestampの分解能を引き受ける。

パターン変更は和音の途中で声部を切らず、次の和音境界でまとめて取り込む。これは自作型を比較するための実験であり、timeline更新を境界予約へ変更する判断ではない。

転回形は第3転回形まで、octaveはコード進行記法の指定を利用する。各声部の跳躍は周回末尾と更新前後を含め最大7半音に制限する。更新が和音境界のどちら側で採用されても制約が守られる候補を選ぶため、自由な音域移動より連続性を優先する。自作型は共通音を保ち、変わる音も同じ境界で切り替え、和音ごとの無音区間を設けない。

当初の比較は単一音色・1trackに限定した。その後userが音色間のcross fadeも両方式で試すことを求めたため、2trackで同じ進行を演奏する範囲へ広げる。音色の候補を別定義するとplayerと分類がずれるため、cat-plugin-playerと同じcatalog readerとRole / Kind分類器を使い、Chord / padから異なる2音色をランダムに選ぶ。発音は引き続きtimelineまたはRustの時計に任せ、5秒保持・5秒fadeの往復をJSで音量へ適用する。

userはさらに、完全に無音になった側で次のランダム音色を準備することを求めた。2trackの音源を交換する方式では、インスタンスの生成・破棄が再生を一時停止する経路を通り、音色準備も同期的に待つ。切り替え時の無音を避けるため、userの指定で対象をSurge XT・Vaporizer2・TyrellN6・Six Sinesに限定し、各2個を事前に作って8trackへ1個ずつ配置する。音源インスタンスは演奏中に保持し、音色だけを読み替える。

この構成の目的は、演奏を途切れさせず次のランダム音色へcrossfadeするため、インスタンスの生成・破棄と音色読み込みを聴こえている演奏から切り離すことだとuserが明示した。各音源を2個ずつ保持するのは、同じ種類の音源同士を切り替える場合にも、現在音を鳴らしたまま別インスタンスへ次の音色を読み込むためである。次の音色は無音側で準備し、準備が整ってからcrossfadeする。読み込みが遅い場合は切り替えを延期して現在音を鳴らし続ける。

AIはこの事前準備をアプリ全体の起動へ広げ、easyのresetでも音源を残し、通常の音源交換も保持へ変更した。userから起動遅延と起動時の8インスタンスを指摘され、目的はevolveのsnippetを使ったときだけevolve modeに入ることだと明示された。通常起動の準備は従来の1音源へ戻し、8音源の準備・再利用はmode内に限定する。

既存の音色とclipを上書きしないため、modeは専用trackを追加して演奏する。evolve間の切り替えと再実行ではそのpoolを再利用し、end evolveまたは通常の演奏snippet・easy初期化/resetで終了して専用trackと周期処理を片付ける。音量変更や保存などの補助操作では維持する。通常の演奏へ自動的に復帰するのではなく、終了時は停止し、既存の音源・clipとloop設定を残す。

Vaporizer2のwavetable参照などが保持時間を超える可能性をuserが指摘したため、読み込み時間を5秒以内と仮定しない。catalogの音色準備はバックグラウンドへ分離し、無音trackのホスト読み込みが完了してから次音の候補へ戻す。読み込み中や失敗したtrackは選ばず、候補がなければ現在の音色を保持する。選んだ次音は無音で発音を準備し、準備が完了してからfadeを始める。JSの時計が止まっても発音時計は進むが、プラグイン自身がホストのメインスレッドを占有する時間まで分離する設計ではない。

userからevolve中の重さと頻繁な音切れが報告され、実装では準備済みの全8インスタンスが音量0の待機中も発音・DSP処理を続けることが分かった。8個の保持は全8個の常時発音を求めるuser決定ではない。この8個同時発音時の音切れを根拠として、userはtimeline型・自作型ともに、同時にnote onを送る対象を現在音と次の音色の最大2インスタンスだけに限定すると決定した。無音での発音準備もこの2個に含め、残りの待機インスタンスへnote onを送らない。4音源各2個の保持と、準備が遅い場合に現在音を維持する目的は継続する。全8個へ演奏を送り音量だけで聴こえる音を選ぶ方式は撤回する。

note onを止めるだけでは既に鳴っている音符やrelease・内蔵effectの処理が残り、無音でもホストからDSPが呼ばれ続ける。このためuserは、役目を終えた音源を無音にしてから音符を確実に終了させ、ホスト側のbypassで待機中のDSP呼び出しを省略する方針も採用した。インスタンスと読み込んだ音色は保持し、次音に選んだときに復帰させる。復帰時に古い音符や残響を持ち越さず、発音準備も含め最大2個を守る。この休止・復帰はevolve内に限定し、通常演奏の処理へ広げない。

自作型で同じ8音色を保持し、8個処理と2個処理を交互に各約6秒・2回ずつ比較すると、CPU使用量は1コアを100%として約226〜228%から73〜83%へ下がり、同期間の音声ブロック数は132〜133から282〜286へ回復した。待機音源の処理削減を支持する結果だが、2個でも各測定に5回の処理期限超過が残った。音色による負荷と他の音切れ要因は残り得るため、この方式だけで音切れの全原因が解消すると断定しない。

## 二方式と8個保持の撤回

固定条件の調査では、timelineの助走中に負のsource位置が0へ丸められ、同じ先頭和音が複数blockへ送られることが分かった。timeline専用の補修でこの重複は除けたが、処理期限超過は残った。userは、AIが二方式の違いを混同して雑に実装したことを不具合の背景と判断し、timeline型と、そのためだけの補修を廃止してRust DLLの自作型へ集中すると決定した。この補修の成功は維持の根拠にしない。

userは同時に、4音源各2個の常設保持を撤回し、A/Bの2インスタンスへ単純化した。Aの演奏開始後すぐBのランダム音色を準備し、Bが準備でき、Aだけの演奏が5秒以上になったらcrossfadeする。Bだけになった時点でAの準備を要求し、逆方向を反復する。準備や失敗からの再試行が遅くても現在音を保持する。従来の5秒linear fadeを継続し、fadeの時計もRustへ移す。JSの応答待ちは準備開始を遅らせ得るが、発音とfadeの進行を止めない。

grid-sequencerの成功例は、演奏側から待機側の準備を分離し、準備完了を待たず現在音を継続する根拠となる。ただしserverの予備プールは2個の決定と両立しないため採用しない。UAPMDの通常のgraph変更・state変更には全体のrender除外があるため、専用の未公開graphを各側に1本ずつ持ち、無音側だけで生成・state読込・破棄する。旧音源を破棄してから新しい音源を生成し、一時的な3個目も保持しない。Rustが無音側の所有権をcontrolへ返すまで、そのgraphを変更しない。これは通常modeの生成・演奏経路を変えずに、Rustの時計とsample単位のfadeへUAPMDを接続するための判断である。専用演奏経路の多重メンテと実装規模の増加はuserが許容した。

未公開graphのDSPをafter callbackへ置くと、UAPMDにworkerがあってもA/Bは直列になる。固定stateの測定では2本が各約17ms、callback全体が34.6msとなり、48kHz・1024 framesの21.33msを超えた。この接続方法は高速な演奏という目的を満たさないため撤回し、専用graphをUAPMDの既存worker jobへ渡すshimを採る。Rustはbefore callbackで発音を準備し、after callbackではgain適用と所有権の返却だけを行う。evolve内はworkerの待ち期限を実際のblock期限とし、通常の80%の早期打切りは通常modeに残す。worker処理が失敗してafter callbackが省かれた場合も、所有権を返すまで無音側を交換しない。並列化で2本の処理時間の加算を避けるが、単一音源の重いblockまで期限内になると保証する判断ではない。

並列化後も間欠的な負荷でworkerの期限超過が残った。同じ固定state・6worker・45秒の比較では、追加のCPU負荷なしで10回だったworker破棄が、別processで1coreを稼働させた条件では0回となり、最大callback時間も21.34msから16.59msへ下がった。cat-smf-editorのADR 0022にも、workerがほぼ全員休むとDSPが遅くなり、1coreの稼働を保つと改善する観測がある。CPUのクロック低下そのものをこの比較だけで断定せず、間欠負荷での実行時間を安定させるため、AIはRust DLLに演奏callbackが来る間だけ1coreを稼働させる処理を採る。約1core分のCPU消費を引き受けるが、callbackが途絶えれば休止し、mode終了では破棄する。

CPU稼働維持だけでは3分の固定試験でworker破棄が1回残ったため、参照実装が併用するTIME_CRITICALもevolveの描画threadへ限定して適用する。一律に15へ設定する案は、MMCSSで既に基準優先度25のworkerを逆に15へ下げ、APIが返す17をそのまま設定し直しても復元できないため撤回する。既存の高い優先度は維持し、通常値で動く描画threadだけを引き上げる。変更した元の優先度をthreadごとに保存し、通常の描画を行う前に復元する。通常modeのworker数や優先度、OSの電源設定やprocess全体の優先度へ変更を広げない。

## 範囲

自作型は選んだ各trackのMIDI入力を所有し、有限個のstepを反復する。evolve専用の2trackにはfreezeを使わず、準備中の音源へ発音を送らない。準備後は無音で和音の発音を待ってからfadeし、役目を終えた側は音符を終了して次の音色へ交換する。通常起動・通常の演奏・loop・freezeの責務へ広げない。重い音源自体の処理期限超過まで解消したと推定しない。

自作型のパターンと専用音源はセッション内だけで、project保存の音符には含めない。timelineには表示専用の1周分を投影する。これは通常clipを増やす方式ではなく、表示には最新の受付済みパターンが現れ、発音側への採用まで最大1和音分先行し得る。通常clipや設定の保存形式は変えず、既存データの移行も生じない。自作型の保存やtrackごとに独立した進行への拡張は対象外とする。
